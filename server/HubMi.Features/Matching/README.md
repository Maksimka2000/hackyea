Public workflow (`POST /api/match`, anonymous, rate limited): accept a description of a social need, find relevant innovations, and return up to 4 with a match indicator, the category of each card, a category header for the whole result and source links. Keep the persistence and model implementations in Infrastructure.

Only two inputs are compared: the user's text and the card text (problem, target group, title, short description, solution). There are no synonym lists, word-form lists or generated sentences. Synonyms are handled by the embedding model (words with a close meaning, such as "babcia" and "osoba starsza", give close vectors). Typos are handled by the model's tokenizer: it splits words into subword pieces, so a small typo changes one or two pieces and the vector moves only a little.

How it works:

1. `MatchRequestValidator` strips markup and checks length (3-1000 characters).
2. `QueryAnalyzer` folds accents (Ł = L), drops stop words and cuts words to 5-letter prefix stems. The stems are used only to explain a match and by the keyword fallback; the embedding model and the reranker always get the natural text.
3. `ITextEmbedder` (local BGE-M3, int8 ONNX, ONNX Runtime on CPU; no text leaves the server and no text is generated) turns the lightly normalized text (trimmed, whitespace collapsed, Unicode NFC; stop words and punctuation are kept because they carry meaning, e.g. "nie") into a normalized 1024-number vector.
4. `IInnovationVectorIndex` (Infrastructure: `PostgresInnovationVectorIndex`, pgvector) orders the rows of the published cards by cosine distance (`<=>`, served by the HNSW index with `vector_cosine_ops`) and keeps each card's best row: `problem` (problem + target group, never the target group alone) or `solution` (title, short description, solution). Similarity is `1 - distance`. It proposes `RetrievalLimit` (7) cards.
5. Early exit: if even the best card's best row is less similar than `RetrievalFloor` (F, 0.30), nothing is returned and the reranker is not run.
6. `IReranker` (bge-reranker-v2-m3, int8 ONNX) reads the user's text together with each of the top `RerankCandidates` (7) cards, one pair at a time in one batch. The card text is `PassageTextBuilder.BuildRerank`: only `Problem: …` then `Rozwiązanie: …` (no title, tagline or target group). The problem comes first, so it carries the most weight and survives if a pair is ever cut to `RerankMaxTokens` (512); at about 3.8 characters per token a problem plus the 600-character solution fits, so normally nothing is cut. Only cards with a score of at least `RerankThreshold` (T, 0.001) are returned, at most `ResultCount` (4); **an empty result is a valid answer** (the web client shows its "nothing found" state). The match percentage follows the reranker's logit: T is 0 %, `RerankCeiling` is 100 %; `GoodThreshold`/`PartialThreshold` apply to it, and confidence is `low` when the best card is below `PartialThreshold`. If the reranker is unavailable, the vector similarity alone is used with the stricter `RetrievalOnlyFloor`.
7. `RelevanceScorer` stays as the explanation: which of the user's words each card contains and in which section. A card can match by meaning with no shared word; then the reason says so and `missingWords` is empty.
8. `MatchExplainer` builds `why` for each card from the card's own stored text only: the sentence that best fits the user's words (problem text when the problem row matched, solution text when the solution row matched; the repeated "Innowacja odpowiada na" lead-in is cut), with `highlights` (start/length in the excerpt) for every word whose accent-folded form starts with a stem of the user's words, so typos and missing diacritics still mark. `byMeaning` is true when the card shares no word with the user; nothing is marked then. `MatchingService` derives the category (always one of the library's 9) by voting with the match percentage of the returned cards (a card that barely passed still counts one vote; an empty result has no category), caches identical questions for `CacheSeconds` (the key includes the index version: row count and latest change of the vectors and of the published cards, so a card edit invalidates it on every instance), and logs the request without personal data. Score lines in the application log carry scores and row kinds only, never the user's text.
9. If the models or the vectors are unavailable (model file missing, no vector stored yet after a first start), matching answers from the keyword fallback (`IInnovationSearch.FindCandidatesAsync`, Postgres full-text search) instead of failing.

Keeping vectors current: `PassageTextBuilder` defines the texts that are embedded and their hashes; the beneficiaries list ("Kto może skorzystać") is left out everywhere because it names institutions, not whose problem a card solves. Problem and solution stay separate rows: one vector for a mixed text is a blend of two topics and is close to neither kind of question. The Infrastructure `InnovationIndexer` embeds the rows whose text or model changed and deletes rows that no longer exist; `VectorIndexRefresher` runs it at startup and whenever the published cards change (checked every `Embeddings:RefreshSeconds`). Vectors are stored in Postgres (`innovation_embedding.vector`, `vector(1024)`, one row per card + kind + ordinal) and searched there, so every instance sees a written row at once. `Embeddings:ModelId` is the model version: change it when the model, pooling or text recipe changes and everything is re-embedded; a model with another vector size also needs a migration of the column. Whatever creates or edits a card (a future admin save or import) can call `IInnovationIndexer.ReindexAsync` for an immediate re-embed; it must also update the card's `UpdatedAt`.

Database: the `vector` extension is created by the migration. Locally and in Docker the `pgvector/pgvector:pg16` image provides it. On Azure Database for PostgreSQL Flexible Server, allow-list `VECTOR` in the `azure.extensions` server parameter before the API migrates. At library size (about 230 rows) Postgres may read every row instead of using the HNSW index; the answer is the same. The index pays off as the library grows. HNSW is approximate: at large sizes it can, rarely, miss a true neighbour.

Results always refer to stored cards and carry their ROPS source link. Tune thresholds and stop words in `search-config.json`; the models, their files and the refresh interval are under `Embeddings` in configuration. Both int8 models need about 1.5-2 GB of RAM.

Model files are not committed: run `server/tools/fetch-model.sh` for local runs (the Docker build does it with pinned revisions and checksums). Check quality with `server/tools/eval-matching.sh` (needs a raised `RateLimiting__Match__PermitLimit`); its query set is `.doc/data/matching-eval.json`, including `none` queries that must return no card. Re-run it, and re-pick T and F, after any change of model, text recipe or cards. The queries were also used to pick the thresholds, so the numbers are optimistic; add queries nobody tuned against for an honest accuracy number. Calibration notes: bge-reranker-v2-m3 is strict with everyday wording (raw scores of 0.001-0.01 are normal for a useful match), so T is far below 0.5. The final values (T = 0.001, F = 0.30) and the tuning table are in `.doc/search-engine.md`; `server/tools/tune-thresholds.sh` repeats the sweep.
