Public workflow (`POST /api/match`, anonymous, rate limited): accept a description of a social need, find relevant innovations, and return the top 3 with a match indicator, the category of each card, a category header for the whole result and source links. Keep the persistence and model implementations in Infrastructure.

How it works:

1. `MatchRequestValidator` strips markup and checks length (3-1000 characters).
2. `QueryAnalyzer` folds accents (Ł = L), drops stop words and cuts words to 5-letter prefix stems. The stems are used only to explain a match and by the keyword fallback. There are no synonym or word-form lists: cards change, so nobody maintains word lists.
3. `ITextEmbedder` (local BGE-M3, int8 ONNX, ONNX Runtime on CPU; no text leaves the server and no text is generated at request time) turns the normalized text (trimmed, whitespace collapsed, Unicode NFC) into a meaning vector. `IInnovationVectorIndex` holds several rows per card and returns each card's best row (cosine, MAX): `problem` (problem + target group, never the target group alone), `solution` (title, short description, solution) and `synthetic` (reviewed everyday-language sentences, one row each; see below). It proposes `RetrievalLimit` (20) cards.
4. Early exit: if even the best card's best row is less similar than `RetrievalFloor` (F), nothing is returned and the reranker is not run.
5. `IReranker` (bge-reranker-v2-m3, int8 ONNX) reads the user's text together with the top `RerankCandidates` (10) cards, using `PassageTextBuilder.BuildRerank` (labelled Tytuł / Problem / Dla kogo / Rozwiązanie, problem first). Only cards with a score of at least `RerankThreshold` (T) are returned, at most `ResultCount`; **an empty result is a valid answer** (the web client shows its "nothing found" state). The match percentage follows the reranker's logit: T is 0 %, `RerankCeiling` is 100 %; `GoodThreshold`/`PartialThreshold` apply to it, and confidence is `low` when the best card is below `PartialThreshold`. If the reranker is unavailable, the vector similarity alone is used with the stricter `RetrievalOnlyFloor`.
6. `RelevanceScorer` stays as the explanation: which of the user's words each card contains and in which section. A card can match by meaning with no shared word; then the reason says so and `missingWords` is empty.
7. `MatchExplainer` builds `why` for each card from the card's own stored text only: the sentence that best fits the user's words (problem text when the problem or a synthetic row matched, solution text when the solution row matched; the repeated "Innowacja odpowiada na" lead-in is cut), with `highlights` (start/length in the excerpt) for every word whose accent-folded form starts with a stem of the user's words, so typos and missing diacritics still mark. `byMeaning` is true when the card shares no word with the user; nothing is marked then. `MatchingService` derives the category (always one of the library's 9) by voting with the match percentage of the returned cards (a card that barely passed still counts one vote; an empty result has no category), caches identical questions for `CacheSeconds` (the key includes the index version, so a card edit invalidates it), and logs the request without personal data. Score lines in the application log carry scores and row kinds only, never the user's text.
8. If the models or the vector index are unavailable (model file missing, index still building after a start), matching answers from the keyword fallback (`IInnovationSearch.FindCandidatesAsync`, Postgres full-text search) instead of failing.

Keeping vectors current: `PassageTextBuilder` defines the texts that are embedded and their hashes; the beneficiaries list ("Kto może skorzystać") is left out everywhere because it names institutions, not whose problem a card solves. The Infrastructure `VectorIndexRefresher` embeds the rows whose text or model changed, deletes rows that no longer exist and reloads the in-memory index, at startup and every `Embeddings:RefreshSeconds`. Vectors are stored in Postgres (`innovation_embedding`, one row per card + kind + ordinal, `real[]`) and searched in memory; the library is small enough that pgvector is not needed. `Embeddings:ModelId` is the model version: change it when the model, pooling or text recipe changes and everything is re-embedded. Whatever creates or edits a card (a future admin save or import) can call `IInnovationIndexer.ReindexAsync` for an immediate refresh on that instance; it must also update the card's `UpdatedAt`.

Synthetic sentences (doc2query): `HubMi.Infrastructure/Imports/SampleData/synthetic-sentences.json` maps a card slug (the part of its source URL after the last comma) to sentences a family member or carer might write. They were generated once with an LLM, never at request time, and are used only for retrieval; they are never shown as card content. **A person must review them**: a sentence that over-promises or drifts to another topic causes false matches. Regenerate a card's sentences when its text changes; editing the file re-embeds the changed rows.

Results always refer to stored cards and carry their ROPS source link. Tune thresholds and stop words in `search-config.json`; the models, their files and the refresh interval are under `Embeddings` in configuration. Both int8 models need about 1.5-2 GB of RAM.

Model files are not committed: run `server/tools/fetch-model.sh` for local runs (the Docker build does it with pinned revisions and checksums). Check quality with `server/tools/eval-matching.sh` (needs a raised `RateLimiting__Match__PermitLimit`); its query set is `.doc/data/matching-eval.json`, including `none` queries that must return no card. Re-run it, and re-pick T and F, after any change of model, text recipe, synthetic sentences or cards. Calibration notes: bge-reranker-v2-m3 is strict with everyday wording (raw scores of 0.001-0.01 are normal for a useful match), so T is far below 0.5.
